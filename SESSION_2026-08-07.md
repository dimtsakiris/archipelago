# Session log — 7 August 2026: Data integrity fix + Identifier property

## Result
150/150 source items confirmed present in Wikibase, each linked to exactly
one unique source row via the new **P14 (identifier)** property.

## What happened
The original import (3 Aug) and a same-day follow-up (7 Aug morning) both
had partial CREATE failures in QuickStatements: a Q-ID would get reserved
but the item creation would not fully complete, leaving "ghost" Q-IDs that
don't resolve (`Item:QNN — This entity does not exist`). Because titles in
the source data repeat (e.g. multiple "Το καΐκι 'Ανάληψη'" entries), there
was no reliable way to tell which source rows were actually missing until
a proper unique-key reconciliation was done.

### Timeline of fixes (chronological)
1. `batch1_fix_p5.qs` — link items to their collection (P5). 98/150 ok,
   52 errors — first sign that ~23+ Q-IDs didn't actually exist.
2. `batch2b/2c` — date fixes (P3/P11), various format issues resolved.
3. `batch2d/2f/2g` — attempts to recreate the ~23 missing items. Discovered:
   - QuickStatements' `-Property` REMOVE syntax hangs forever against a
     non-existent Q-ID (never do `ADD` to a ghost Q-ID).
   - Correct REMOVE syntax is `-QID|P|value` (minus before the Q-ID).
   - A source-column read bug swapped creator ↔ description for a while.
   - Backslash-escaping quotes corrupts labels on this QuickStatements
     instance; convert embedded `"` → `'` instead (matches the original
     working `build_import.py`'s `qs_string()` helper).
   - Wikibase rejects an item whose label and description are identical
     in the same language — drop the description in that case.
   - Running the same CREATE batch twice (by accident) makes duplicates;
     only `-QID|P1|Q1` (removing the instance-of statement) is reliably
     supported for cleanup — item-level delete needs Administrator rights,
     which this account does not have on wikibase.cloud.
4. **Root fix**: created property **P14 "Αναγνωριστικό" (identifier)**,
   string datatype, and backfilled the source spreadsheet's `identifier`
   column onto every item (`batch3a_backfill_identifiers.qs`). Errors from
   that batch = the *definitive* list of genuinely-missing rows (25 of
   them), since ADD-statement-to-ghost-QID fails cleanly and countably.
5. `batch4/5/6` — recreated the 25 truly-missing rows with the identifier
   included from the start.
6. `batch7_clean_orphans.qs` — also discovered 8 leftover ghost-adjacent
   duplicates from the *original* 3 Aug import (same root cause, never
   cleaned up at the time). Removed their P1 statement so they're inert.

## Current data model addition
```json
"identifier": { "pid": "P14", "datatype": "String" }
```
Every future import/fix script should set P14 = the source `identifier`
column immediately on CREATE, and any reconciliation task should key off
P14, not label/title matching.

## Verification query (source of truth going forward)
```sparql
PREFIX wd: <https://archipelago-wikibase.wikibase.cloud/entity/>
PREFIX wdt: <https://archipelago-wikibase.wikibase.cloud/prop/direct/>
SELECT (COUNT(DISTINCT ?id) AS ?uniqueIdentifiers) WHERE {
  ?item wdt:P1 wd:Q1 .
  ?item wdt:P14 ?id .
}
# Expect: 150
```
